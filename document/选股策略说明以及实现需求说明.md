# 选股策略说明与实施落地方案

更新时间：2026-04-15

本文档用于将“策略选股整理、回测验证、模板沉淀、模拟盘联动、后续实盘扩展”这些目标，改造成当前项目可执行、可分阶段交付、可验收的实施方案。

本文档不是泛化愿景说明，而是后续开发、测试、验收、迭代的执行基线。

---

## 1. 背景与目标

当前项目已经具备以下基础能力：

1. 综合选股与策略选股能力，已有较多策略条件与选股结果数据。
2. 回测基础能力，已有组合回测引擎、策略编辑页、回测历史页、回测详情页、回测对比页。
3. 模拟交易基础模块，项目内已存在 `paper_trading` 目录与相关页面/接口基础。
4. 测试基础，已有 `tests/test_portfolio_backtest.py`、`tests/test_backtest_metrics.py`、`tests/test_backtest_dashboard_date_range.py` 等回测相关测试。

本次文档优化的核心目标是：

1. 将“策略选股”中的策略沉淀为结构化策略说明文档。
2. 将策略说明映射为可运行、可回测、可测试的策略模板。
3. 统一策略文档、策略实现、回测验证、模拟盘联动之间的口径。
4. 为后续多策略比较、参数优化、模拟盘/实盘扩展预留稳定架构。

## 4. 总体实施原则

后续所有策略整理、实现与测试，必须遵循以下原则：

1. 文档先行
	任何策略进入模板库前，必须先形成标准化说明文档。

2. 先可回测，再谈调优
	没有稳定回测口径的策略，不进入优化阶段。

3. 禁止未来函数
	仅允许使用信号日及之前已知数据，禁止用未来价格、未来财务数据、未来事件信息生成当日信号。

4. 禁止过拟合导向的硬编码
	不允许为单一时间段或少量样本特意构造过窄参数范围。

5. 说明、实现、测试三者一致
	策略说明中的条件、策略模板中的逻辑、测试中的断言必须一一对应。

6. 与聚宽风格接口保持兼容
	策略模板优先采用当前项目已支持的聚宽风格接口子集，便于互相验证。

7. 单策略独立运行
	每个策略必须可以独立回测、独立测试、独立展示，不依赖其它策略的运行结果。

## 6. 策略文档标准

后续整理“策略选股说明”时，每个策略必须使用统一结构，至少包含以下字段：

### 6.1 基本信息

1. 策略名称
2. 策略分类
	- 技术形态类
	- 趋势突破类
	- 回调反转类
	- 基本面筛选类
	- 复合因子类
3. 策略来源
	- 项目原有策略
	- 页面策略选股条件整理
	- 经验规则补充
4. 适用标的范围
	- A股主板
	- 创业板
	- ETF
	- 指数成份股等

### 6.2 信号定义

1. 买入信号条件
2. 卖出信号条件
3. 若原策略只有选股没有卖出逻辑，需要补充标准退出逻辑
	可选方式：
	- 固定持有 N 天
	- 止盈止损
	- 趋势反转卖出
	- 再平衡调仓
4. 信号触发时点
	- 收盘后生成，次日开盘执行
	- 当日开盘前生成，当日开盘执行
	- 按周调仓
	- 按月调仓

### 6.3 数据口径

1. 使用的数据表/字段
2. 使用的时间窗口
3. 财务字段的公告口径与可用时点
4. 是否依赖缓存历史数据或衍生指标表

### 6.4 风险约束

1. 是否限制单票仓位
2. 是否限制最大持仓数
3. 是否限制行业集中度
4. 是否过滤 ST、停牌、上市天数不足、成交额过低股票

### 6.5 回测配置建议

1. 推荐回测区间
2. 推荐初始资金
3. 推荐基准指数
4. 推荐调仓频率
5. 推荐手续费、印花税、滑点参数

### 6.6 风险提示

1. 该策略可能失效的市场环境
2. 容易被误用的参数
3. 是否对数据质量特别敏感

## 7. 策略实现标准

将策略文档转换为策略模板时，必须满足以下要求：

### 7.1 模板命名

1. 模板名称与“策略选股”中的策略名称一致。
2. 模板描述中注明来源、版本、适用范围。

### 7.2 模板接口风格

优先使用当前项目已支持的聚宽风格接口子集，例如：

1. `initialize(context)`
2. `handle_data(context, data)`
3. `history()`
4. `order_value()`
5. `order_target()`
6. `order_target_value()`

如果某个策略需要扩展新的上下文能力，应先补能力层，再落策略，不允许在策略代码中硬写数据库读取或绕过沙箱。

### 7.3 模板最小要求

每个模板必须明确：

1. 选股池来源
2. 调仓频率
3. 买入条件
4. 卖出条件
5. 仓位分配方式
6. 风险控制条件

### 7.4 不允许的实现方式

1. 在策略代码中直接访问未来日期数据。
2. 在策略代码中通过文件或网络临时读取未纳入回测口径的数据。
3. 在策略代码中硬编码只对单一股票或单一时间段有效的逻辑，除非该策略本身就是单标的策略。
4. 将策略说明中没有定义的临时规则偷偷加入实现。

## 8. 策略审核规则

策略进入模板库前，必须通过审核。审核维度如下：

### 8.1 可行性审核

1. 策略条件是否能映射到项目已有数据。
2. 是否能够在回测引擎中表达。
3. 是否存在无法确定执行时点的条件。

### 8.2 准确性审核

1. 文档条件与代码条件是否一致。
2. 条件边界是否清楚，例如 `>`、`>=`、窗口长度、基准比较方式。
3. 财务字段是否明确采用可回测口径，而不是事后修正口径。

### 8.3 量化可交易性审核

1. 是否有明确的买卖逻辑。
2. 是否可以形成订单。
3. 是否考虑停牌、涨跌停、流动性等现实约束。

### 8.4 风险审核

1. 是否存在未来函数。
2. 是否明显过拟合。
3. 是否存在样本内调参过多而缺少样本外验证。

审核结论建议统一分为：

1. `通过`：可进入模板库。
2. `需调整`：文档或参数需修改后重审。
3. `不通过`：不适合当前项目落地。

## 10. 分阶段实施计划

本需求建议分 6 个阶段推进，避免一次性铺太大导致文档、代码、测试不同步。

### Phase 1：策略盘点与说明文档整理

目标：先把现有策略定义梳理清楚。

主要任务：

1. 盘点“策略选股”中当前已有的所有策略。
2. 将每个策略整理成统一格式的说明条目。
3. 标记每个策略的数据依赖、买卖逻辑完整性、可交易性问题。
4. 输出首版 `document/策略选股说明.md`。

交付物：

1. 策略清单总表。
2. 每个策略的标准说明。
3. 每个策略的审核状态。

验收标准：

1. 所有现有策略都能在文档中找到。
2. 每个策略都有明确买入逻辑。
3. 对没有原生卖出逻辑的策略，文档中明确补充退出规则。

### Phase 2：策略模板化落地

目标：把通过审核的策略转为可运行模板。

主要任务：

1. 将通过审核的策略逐个实现为模板策略。
2. 在策略列表中沉淀模板，名称与原策略一致。
3. 补齐必要的模板元数据，例如描述、推荐参数、默认回测区间。

交付物：

1. 策略模板库第一批可运行模板。
2. 模板映射表，记录“文档条目 -> 模板名称 -> 实现版本”。

验收标准：

1. 每个模板可在编辑页直接运行回测。
2. 模板不依赖人工补充临时代码才能运行。
3. 模板逻辑与文档描述一致。

### Phase 3：测试与验证闭环

目标：保证策略模板可运行、可复现、可独立验证。

主要任务：

1. 为每个模板增加最小运行测试。
2. 增加未来函数与可疑逻辑检测测试。
3. 增加典型回测区间的基线快照测试或指标阈值测试。
4. 验证新模板不影响已有回测模块。

交付物：

1. 策略模板测试集。
2. 回测验证报告。

验收标准：

1. 每个模板至少有 1 个独立测试用例。
2. 回测测试通过率达到预期。
3. 现有回测与看板相关测试不回归。

### Phase 4：策略对比与展示增强

目标：提升策略间的横向比较能力。

主要任务：

1. 补齐回测结果跨策略对比字段。
2. 规范图表对比与表格对比的口径。
3. 增加收益率、回撤、胜率、盈亏比、交易次数等指标排序。
4. 优化默认排序规则，默认按收益率降序。

交付物：

1. 策略回测比较视图增强。
2. 对比指标口径说明。

验收标准：

1. 用户可以在页面上完成多策略结果对比。
2. 图表与表格数据口径一致。
3. 默认排序逻辑符合预期。

### Phase 5：模拟盘接入与多账户扩展

目标：让已验证策略具备接入模拟盘的统一规范。

主要任务：

1. 定义策略接入模拟盘的最小元数据要求。
2. 支持一个账户运行多个策略，或一个策略运行多个账户实例。
3. 保存交易记录、收益曲线、阶段指标。
4. 提供策略间、账户间的对比能力。

交付物：

1. 模拟盘接入规范。
2. 多策略多账户状态管理方案。
3. 模拟盘展示页增强方案。

验收标准：

1. 模拟盘可查看交易、持仓、收益与主要指标。
2. 支持不同策略之间的对比。
3. 多账户运行时数据不串扰。

### Phase 6：参数调优与历史留痕

目标：支持后续参数优化，但不破坏回测可追溯性。

主要任务：

1. 为每个策略记录参数版本。
2. 记录调优前后回测结果。
3. 支持查看参数历史与结果差异。
4. 为后续更系统的参数寻优预留结构。

交付物：

1. 参数版本模型。
2. 参数调优记录与对比机制。

验收标准：

1. 能够查看某个策略的历史参数版本。
2. 能比较调整前后结果差异。
3. 不覆盖原始基线结果。

## 12. 测试与验证要求

所有策略实施必须遵守以下测试要求：

### 12.1 必测项

1. 策略代码可通过沙箱校验。
2. 策略可正常编译。
3. 策略在最小测试数据集上可运行。
4. 策略在标准回测区间可运行。
5. 策略结果结构完整，至少包含净值、交易、指标。

### 12.2 推荐测试项

1. 信号日期不晚于所依赖数据的可见日期。
2. 核心条件单元测试。
3. 指标边界测试。

1. 是否复用现有模块而非重复造轮子。
2. 是否为多策略、多账户、参数调优预留扩展点。
